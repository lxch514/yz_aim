```sh
ssh -p 6204 root@47.102.210.95
```

控制终端启动：

```sh
cd /root/yz_aim_can0_double
./build/yz_aim_can0 --if can0 --node 1 --node2 2
```

另开一个SSH终端，启动同目录的独立通信监测脚本：

```sh
cd /root/yz_aim_can0_double
python3 -B can_monitor.py
```

默认每60秒中文汇总，异常即时中文输出。不打开CAN接口、不发送CAN命令、不使能电机；
退出监测脚本不影响控制程序。需要实时逐帧刷屏时只在监测终端运行：

```sh
python3 -B can_monitor.py --frames
```

控制终端不会打印CAN或心跳逐帧信息。主程序异步记录所有已采集的详细通讯帧；
监测脚本自动跟随本程序最新会话，并把中文汇总和异常也追加到同一份
`logs/can-frames-<时间>-<进程号>.log`。位置偏差仍在 `logs/motion-*.csv`。
启动加 `--no-trace` 会关闭通讯帧记录，监测脚本将没有该会话的新数据。

统计包括发送/接收、节点1/2 SDO、主站0x77F心跳与节点心跳、最大有效心跳间隔、
SDO读重发、未确认超时、SDO拒绝、接收队列明确丢弃、诊断队列丢弃和日志输出异常。
TX仅表示传输层接受；主站心跳为单向发送，TX/RX总数不应强行相等。
未确认请求可能来自应答延迟、通信丢失或诊断记录缺失，不等于已证实的物理丢帧。
未使能且不发主站心跳时的0x0020通信报警以中文提示说明，避免误判为正在运行时掉线。

程序提示符内逐条输入：

```text
sync-status
sync-enable
sync-zero
extend 10 200
retract 10 200
sync-status
```

extend默认节点1负转、节点2正转；retract反向。速度单位电机RPM，时间单位毫秒。
后续按现场行程选择 `extend 300 10000` 或 `retract 300 10000`，不要把不明行程当作默认测试。
结束时 `sync-disable`、`quit`；定时运动中Ctrl+C要求停止。
`sync-run 100` 伸出常转、`sync-run -100` 缩进常转，用 `sync-stop` 停止。

零点：先将机构放到正确初始位置并确认齐平，静止时执行 `sync-zero`。
这是固定软件零点，不写设备编码器，不自动移动或回零；同一会话保留，重启后需重新设置。

之前“不动作”的证据：17:44那条300RPM/10000ms命令实际运动满10秒；17:45下一条命令
在节点2的0x60FF速度目标写入确认处超时，随后安全锁止会话。新版本将双轴配对确认窗口
从120ms调整为300ms，仍受动作截止时间约束、继续维护共享心跳，不盲目重发写入。
故障后提示符显示“故障需重启”，运动命令明确要求quit重启，不伪装成仍可运行。
同一目录同一CAN接口仅允许一份控制程序，避免并发会话交错SDO。

实机验证：最终运动控制逻辑以10RPM、各200ms执行一次伸出/缩进，两轴均有编码器位移，
各停止请求均为200ms，最大有效偏差分别0.0267°和0.0392°，结束确认两轴失能。
长行程、300RPM长时间运作不属于此次低速实机验收范围。
