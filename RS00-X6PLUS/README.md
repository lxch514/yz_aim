# RS00 + X6 PLUS 共用 CAN0 通信测试

只在本目录修改程序。`/root/RS00` 及原有测试日志保持原样。
本版本修正协议计数和诊断缺陷，并提供板上位时序对照。实测结果见随附检查报告；只有实际完成的测试才能作为稳定性证据。

## 不驱动设备的检查

```bash
cd /root/RS00-X6PLUS
python3 -B tools/selftest_x6.py
python3 -B tools/regression_v2.py
python3 -B tools/observe_bus.py --seconds 30
python3 -B x6test.py --check-only --motor-id 127
```

前两项完全离线，不打开真实 CAN；`observe_bus.py` 只收不发、不重配接口。
`--check-only` 只读取电机参数并接收遥测，不使能、不发风机控制帧，也不重配接口。
若控制器已处于 ERROR-PASSIVE，它不会自行恢复；被动观察会如实记录。

## 会驱动设备的测试

请在现场具备运动测试条件、同一路 CAN 上没有其它控制程序时启动。
本套件使用控制锁避免自身重复启动；无法阻止其它程序发送控制帧。
`run_test.sh` 会把所选接口 down/up，配置为经典 CAN、1Mbps、请求采样点 0.833（本板量化为0.828）。
板上对照发现原SJW=1会出现接收侧错误，SJW=8的一分钟联合测试通过；随后连续约14分钟运行至用户主动停止，读写超时、控制器错误增量、发送失败和风机重复遥测均为0。完整30分钟由用户自行验证。默认SJW=8；环境变量仍支持对照，其他板卡须重新验证。

```bash
cd /root/RS00-X6PLUS
./run_test.sh 1 500                      # 电机动作 + 风机油门500，短测
./run_test.sh 30 500                     # 同动作，30分钟
./run_test.sh 30 0 --fan-disabled         # 电机动作；电调接入，仅接收其遥测
./run_test.sh 30 0 --no-fan               # 不控制和解析风机；不是物理断开风机
```

注意：`油门0`仍会走风机使能流程；要做到“不发风机控制”，使用 `--fan-disabled`。
“不控制风机”不代表电调不向 CAN0 发遥测。只有实际断开电调，才能形成“只有电机”的硬件对照。

## 通信节拍

- 电机：每70ms写位置、读角度、读速度；读等待50ms，写等待100ms。
- 电机自动上报：设定50ms；统计采用实测中位周期，不能用设定周期直接算丢失率。
- 风机：RawCommand每20ms一次（50Hz），与单独风机参考程序相同。
- 本地EAGAIN/ENOBUFS只限时重试5ms，保留errno计数；不无限等待、不把发送失败混成应答超时。
- 电机电压额外每1秒读一次，写入events.jsonl；可用 `--vbus-sec 0` 关闭进行原节拍对照。
- 接收按最多64帧或2ms分批排空，防止风机遥测积压，同时让油门调度及时得到执行。

目前日志里成功应答大多在1ms附近；整体失联不能靠单纯增加50/100ms等待上限解决。
不自动写电调上报频率：Set/Get Freq写操作会保存Flash。也不修改设备ID、波特率或方向。

## 协议和判读修正

- 风机TID按RawCommand、ReadyControl及每个目标的服务流独立递增、模32回绕。
- 遥测“完全重复”要求同节点、同消息、同TID、同数据且接收间隔小于2秒。
- 同TID数据变化、TID疑似缺口、长间隔回绕/重启歧义分别记录，不把估算写成物理丢帧率。
- 风机在线状态按所有原始遥测刷新；非重复更新间隔另列，避免把重复帧误报成掉线。
- 广播遥测不要求主机逐帧应答；不再断言重复遥测必定来自“主机没回复”。
- RS00回复核对来源电机ID、目标主机ID、数据长度；参数读取另核对索引和内核到达时间，拒绝过期帧确认新请求。
- 写反馈没有事务序号，因此无法在协议层证明每一条写指令和反馈严格一一对应，报告会保留这个限制。
- 0x18与0x02均解析角度、速度、温度及状态/故障位。
- 风机状态bit13表示电调内部CAN-MCU与TI-MCU通信异常，不能直接等同于板子CAN总线故障。

## 新日志

每次运行生成独立、含微秒时间戳的目录，旧日志不重写。

- `can-frames.log`：电机逐帧和风机抽样记录；不是总线完整抓包。
- `test.log`：动作进度与通信小结。
- `bus-health.jsonl`：每秒控制器状态、berr_counter、CAN专用xstats和收发增量。
- `events.jsonl`：发送errno、应答超时、CAN错误帧、状态切换、重复样本、电压与收尾确认。
- `summary.json`：最终统计、诊断、逐电调/逐消息TID和范围数据。
- 中文总结：明确区分流程`outcome`与通信验收`validation`。

SO_TIMESTAMPNS优先记录内核接收时刻，并计算内核到程序读取的延迟；不支持时明确报告。
SO_RXQ_OVFL统计本socket接收队列丢弃；普通recv异常不再冒充“缓冲溢出”。
CAN_RAW_ERR_FILTER接收错误帧；驱动不支持/未开启berr-reporting时，捕获可能不完整，需交叉看xstats。
内核时间戳仍受驱动和系统时钟限制，不等于硬件总线分析仪时间戳。

## 如何判断通过

`outcome=completed`只代表动作流程和收尾完成，不代表通信无异常。
通信验收会关注发送失败、应答超时、心跳缺口阈值、末尾静默、CAN专用错误计数增长、错误帧、
接收队列丢弃、风机遥测过期和油门调度迟延。诊断数据缺失也会列出，不能当成“零错误”。
不以普通rx_errors/tx_errors为0排除总线异常；本板已有ERROR-PASSIVE而普通计数仍为0的记录。

电机停止须收到停止后的状态反馈且速度接近0；风机收尾记录零油门成功入队数和失能帧入队结果。
发送成功只表示内核接受帧，不能保证电调已经执行或停转，无法确认时会明确注明。

回滚包保存在本目录 `.backup-review-*.tar.gz`，仅包含本次修改前的程序文件。

Ctrl+C会执行停止收尾，记录outcome=interrupted、validation=incomplete并返回130；这不是完整时长通过。正常跑完应查看validation=pass，不能只看completed。

## 按报告确认的丢失帧逐帧读取位置和速度

心跳设定仍保持默认50ms；不再用固定50ms空窗触发额外读取。实际设备上报约55ms，
因此固定50ms空窗不等于丢失帧，旧版会把报告中的1帧放大为121组读取。

现在实时诊断和最终报告共用同一判据：以启动校准后的实测参考周期计算，
间隔大于1.5倍参考周期时，少帧数为max(0, round(间隔/参考周期)-1)。
校准参考周期在本轮固定，并单独写入报告，避免最终重新估算与已执行诊断次数不一致。

每确认丢失1帧，只安排1组读取：0x7019当前位置（rad）与0x701B当前速度（rad/s）。
丢失1帧就是1组；丢失16帧就是16组；同一缺口少3帧就是3组，不会因等待或持续静默反复读取同一帧。
正常收到心跳且没有确认少帧时，不增加任何位置/速度诊断请求。0x701E/0x701F仍是KP参数。

心跳是设备主动上报，通常到下一帧到达后才能通过相邻间隔确认少帧；两个数值是确认缺帧后
读到的实时值，不是预计缺帧时刻的历史快照。若当前有请求在等应答，先完成该请求再读取，
不覆盖应答匹配；两项沿用原read-ms上限，某项失败仍尝试另一项。

新test.log按丢失帧编号记录确认、读取时间、两个参数的值/状态/耗时；中文总结每丢失1帧
只列1行位置+速度，并对照“估算丢失帧数 / 诊断组数 / 已执行组数”。summary.json中的
heartbeat.loss_metrics及stats.heartbeat_loss_events/heartbeat_position_probes保留结构化明细。

正常结束会完成已确认的排队读取；用户中断或故障中止时，未执行项保留空值并明确标注。
持续无心跳而尚未收到恢复帧的尾段仍单列静默时长和失联状态，不按空窗不断发送请求。
本功能只影响以后运行的新日志，已结束的历史报告不回填、不修改。
