Transport: classic CAN standard 11-bit frames, at most 8 data bytes. User must select one of 125/250/500/1000 kbit/s; the manual does not identify the currently installed motor bitrate. Node 1 is the *manual example*; it was also observed responding on this particular 2026-09-27 bench session, without establishing a generic/default node for other devices. SDO requests `0x600+node`, replies `0x580+node`, DLC 8, little-endian expedited transfers. Read command `0x40` expects `0x4F`/`0x4B`/`0x43` for 1/2/4 bytes; write `0x2F`/`0x2B`/`0x23` expects `0x60` with the exact requested index/subindex. `0x80` preserves the abort code. Before each request, the SDO client empties the receive backlog within both a 200ms and 4096-frame bound (or the caller's earlier deadline), rejecting the transaction without transmission when the FIFO cannot be cleared. The bounds account for periodic PDOs accumulated during a confirmation dialog; they do not certify an unlimited adapter queue. For expedited uploads, the command byte, index/subindex, DLC and declared width must match; unused bytes beyond that width are ignored because a real signed16 `0x606C=-1` reply uses `4B 6C 60 00 FF FF FF FF`. A matching-object malformed reply, ambiguous send failure, or timeout poisons the session; further ordinary requests require closing and reopening the transport. An emergency held-stop frame can still be sent once when motion/output was attempted, **without claiming an acknowledgement**. Other objects and unrelated bus frames do not satisfy an ACK. One-way setpoint/control writes never retry automatically. A previous, delayed ACK for an identical object cannot be distinguished on CANopen; after ambiguous write failure the driver latches unsafe and prevents further automatic operations.

Current movement requires fresh readback, explicit ARM and owned ENABLE. The `m/M` step selector remains 5°/15°/30°/90° output angle, approximately 23211/69632/139264/417792 motor pulses; these are UI conveniences, not a total travel cap. The heartbeat consumer is installed during ENABLE, after old setpoints and operation bits are cleared; each motion reuses the owned watchdog. Position commands hold first, select mode `0x6060=1`, zero the velocity target, set chosen profile speed at `0x6081` (1..3000 RPM, default 30), write existing motion acceleration `0x6083=500 RPM/s`, set target `0x607A`, and use the documented absolute `0x002F` or relative `0x004F`→`0x005F` controlword sequence. Absolute coordinates and relative-coordinate results must remain in the manual's ±1966080000 motor-pulse range; relative deltas must also fit signed32. Position completion requires a fresh reached status, actual position within 16 pulses and stationary speed, then a confirmed hold. Position motion is budgeted as `5000 + 2 × ceil(rpm × 1000 / 500) + ceil(abs(delta_pulses) × 60000 / (rpm × 32768))` ms, with a separate 10 s STOP budget and up to 7 s of stationary confirmation; these are software deadlines, not proof of physical braking. The previous 90°/30 RPM 30500 ms example is historical only. Jog uses the selected nonzero speed (at most 3000 motor RPM) for its bounded 250 ms interval and attempts hold after completion/cancellation. Other producers' watchdog consumers block owned control; the driver does not overwrite them. While the session owns enabled output, the motor worker sends operational heartbeat `0x77F:05` during motion and idle. Only after confirmed disable does cleanup restore previous `0x1016:1` and retire heartbeat; failures leave an unsafe state for inspection. The temporary watchdog timeout is 1000 ms; `service_watchdog` rejects a heartbeat more than 700 ms after the prior one. A heartbeat resumed after timeout may **resume** motion, so faults do not auto-recover by sending it. Node 127 cannot own this producer heartbeat.

Volatile maintenance writes require freshly observed stationary, alarm-free, output-disabled status, with post-write readback: profile RPM 0..3000 (`0x6081`), acceleration 10..1000 RPM/s (`0x6083`; vendor assigns **different meaning** to some special values and limit setup), and current limit `0x261D` in 10mA steps 10..10000. Current-limit low decimal digit controls alarm duration; this API deliberately requires units digit zero rather than implicitly selecting a duration. Do not save these settings automatically.

Node staging: `0x2615` u16 new ID 1..127, `0x2614` u16 `1` generic save, poll until `2`. Keep communicating on the original ID until separate power-cycle and confirmation; do not switch automatically. Bitrate staging returns only an ACK for each staged step; no installed CAN bitrate is confirmed until a separate power cycle and fresh read-only reconnect on the selected bitrate. Bitrate staging: **exact** §7.13 sequence `0x2600` u16 `1`, `0x6083` u32 `800/801/802/803` for 125/250/500/1000 kbit/s, `0x2604` u16 `129`, `0x2600` u16 `506`; no generic save. These unusual writes intentionally override the general object table meanings only within this gated documented procedure, become effective after power cycle, and cannot be automatically retried on partial failure. The manual's example has a printed save-address discrepancy (`26000010` in prose versus SDO frame `0x2614` and OD `26140010`), so this implementation uses the concrete frame/OD only for generic save1. Special TPDO save5 is **not** this operation.
